# kingsSafe 内存窥探检测与响应专项调研

调研日期：2026 年 10 月 29 日；关联实测更新：10 月 30 日。状态：内存窥探、自终止及双进程实验仍未实施，保护效果、兼容性和性能验收均为 not-run。另有[Mac Mono 字段自动改写机制探针](build-hardening-feasibility.md)，仅验证受控字段写入及协调修改/完整旧状态回放反例，不表示本专项的外部读取检测已完成。

## 目标与结论

研究一个随 Unity 插件自动进入构建产物的内存防护机制：游戏团队只引入插件，继续使用原有 Build；插件自动加入探测与保护，在发现符合处置条件的调试、窥探或篡改后阻断相关访问或终止自身应用。正常玩家的功能、资源与体验保持，性能代价单独测量。

“类似量子不可观测”作为产品探索的直觉，工程上拆成访问探测、调试检测、篡改校验与异常响应。它不是物理上的不可观测性，也不能先假定普通客户端能获知每一次外部内存读取。

资料支持的结论如下，涉及 kingsSafe 的实现均为工程判断或待验证候选。

| 判断 | 结论 |
| --- | --- |
| 引入插件后自动带入监测组件 | 在固定 Unity 与目标平台范围内有实现基础；需要实际 Player 验证 |
| 部分调试、异常访问和数据篡改可检测 | 可研究，事件种类、权限、时序与覆盖范围必须分别定义 |
| 少量独立内存区域的访问告警 | 值得做双进程原型，不能直接套到整个 Unity 托管堆 |
| 任意外部读取发生时都能通知游戏并抢先退出 | 所查公开接口不能支持这一普遍承诺；当前不能作为已成立架构假设 |
| 终止游戏即证明数据未被读取 | 不成立，读取可能已经完成；必须以读取方实际获得的数据判定 |
| Windows 原生机制直接复用到 Android 与 iOS | 不成立，需要平台独立实现、签名与发行验证 |
| 任意原游戏中强制退出且绝不损坏正在写入的存档 | 无通用保证；必须检验原有写入、取消与原子提交语义 |

建议继续投入的路线是构建期自动注入与受保护存储，加上平台特定探测；“被窥探即终止自身应用”保留为明确事件下的待验证响应目标。是否实际阻断信息获得，由实验决定。

## 零业务改动是产品约束

接入合格标准是团队只添加 kingsSafe 包，不要求手工修改 C# 调用、字段类型、场景、Prefab、资源目录、加载入口、构建脚本或接入处置回调。自动配置、平台运行组件和中间产物修改由插件承担。

引入插件本身产生的包注册与锁文件变化允许存在；项目原始内容和原有配置不应被插件永久改写。变换仅发生在本次构建的工作副本与输出。开发、Profiler 与诊断所需策略由构建类型自动区分，不能迫使团队修改业务代码才能正常调试。

自动扫描可以判断一部分静态兼容条件，但不能凭字段名可靠理解所有游戏规则。默认策略可覆盖静态证明可处理的对象，必须输出未覆盖对象和原因。一个项目必须依赖业务改造才能工作时，应记为该版本不支持，不能把手工改造样本计入零改动验收。

这项约束不自动推出任意项目全部字段和全部资源均可保护。覆盖范围、源码不变和防护效果是三个独立指标，分别报告。

## 明确威胁与观测事件

| 事件 | 是否必然改变目标数据 | 普通插件可获得的证据 | 需要单独报告的边界 |
| --- | --- | --- | --- |
| 用户态调试器附加 | 不一定 | 平台公开调试状态等信号 | 启动前附加、暂停全进程、结果被修补、合法诊断 |
| 另一进程只读内存 | 不一定 | 特定内存页的异常或状态变化候选 | 普通可读热页、窄范围读取、既有句柄与更高权限 |
| 批量扫描 | 不一定 | 诱饵页被触及等弱信号候选 | 扫描不触及诱饵、系统预取与正常诊断干扰 |
| 修改、冻结或重放数据 | 是，或阻止合法变化 | 受保护表示、校验与进展检查 | 自洽旧状态、修改返回值、同时修补校验 |
| 修改保护代码或执行路径 | 是 | 所选区域的完整性检查 | JIT、重定位、合法 Hook、检查器本身被修改 |
| 内核读取、物理内存或 DMA | 不一定 | 普通应用无完整可见性 | 作为独立权限层实验，不承诺由插件全面感知 |

检测调试器存在不等于识别恶意，读取权限存在不等于已经读取，读取被拒绝不等于插件检测成功。来自一个底层现象的多个派生信号也不能简单视为独立证据。

## Windows 路线

### 调试检测

IsDebuggerPresent 能检查当前进程是否处于用户态调试器上下文。这是明确、有限的能力，不是所有观察行为的检测器。[Microsoft 调试状态接口](https://learn.microsoft.com/en-us/windows/win32/api/debugapi/nf-debugapi-isdebuggerpresent)

候选是在启动和后续检查点获取多类证据，并保护监测组件的完整性。检查频率决定时间窗口，异步轮询不等同于同步拦截。若整个进程被暂停，进程内线程无法按预期继续检查；这项工程限制需用启动前附加和运行时暂停两种实验确认。

不以进程名称、窗口名称、低帧率或单次计时异常直接判定攻击并终止游戏。

### 独立内存页与访问告警

Windows 的 PAGE_GUARD 提供一次性内存页访问告警。首次访问会清除守卫属性；系统服务路径中触发时，该服务可能失败，随后再次访问的结果又不同。[Microsoft 守卫页语义](https://learn.microsoft.com/en-us/windows/win32/memory/creating-guard-pages)

由此得到的研究要求：必须分开测试本进程读取、另一进程读取、反复读取和与合法访问交错读取。不能用本进程触发异常的演示，证明外部读取一定会送达目标进程的异常处理器。异常归属、返回状态、守卫状态变化和读取结果都要采集。

VirtualProtect 以页为粒度。官方提醒不要随意修改普通堆内存块的页权限，因为同一页可能承载多个内存块，堆管理器有自己的读写假设。[Microsoft 页保护约束](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-virtualprotect)

因此，候选仅作用于 kingsSafe 独立分配和管理的少量内存区域。不能把整个 Unity 堆设为访问即告警，也不能把正常 GC、引擎或第三方插件访问当作窥探。保护打开后的暴露窗口、跨线程访问、异常处理重入和 CPU 开销均需验证。

### 诱饵页与扫描探测

研究独立诱饵区域的驻留、保护状态与访问异常能否提供扫描线索。QueryWorkingSetEx 返回的是指定页的状态，公开结构包含 Valid、Shared、保护属性等，不提供某次读取的调用方身份或完整访问日志。[页状态查询](https://learn.microsoft.com/en-us/windows/win32/api/psapi/nf-psapi-queryworkingsetex)、[返回结构](https://learn.microsoft.com/en-us/windows/win32/api/psapi/ns-psapi-psapi_working_set_ex_block)

“状态变化能可靠归因到恶意扫描”属于待证假设。未接触诱饵区域的读取会漏报；系统与正常软件造成的变化会影响归因。该路线先作为研究信号，不单独触发正式版本强制退出。

### 外部读取和驱动边界

ReadProcessMemory 在调用方进程读取目标地址范围，需要相应进程句柄及读取权限。其公开契约没有提供目标应用逐次获知读取的通知。[Microsoft 外部读取接口](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-readprocessmemory)

工程结论是不能从“能读取本进程调试状态”推导出“能感知所有 ReadProcessMemory”。对特定不可访问页的读取失败，也不能证明其他可读页受到了同等保护。

内核的 ObRegisterCallbacks 可观察进程与线程句柄相关操作，但它是驱动接口，回调需要签名内核映像。它不是逐次内存读取回调。[句柄回调](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/wdm/nf-wdm-obregistercallbacks)

所核对的 OB_PRE_CREATE_HANDLE_INFORMATION 文档列出了可修改的权限，并明确只能移除其列明的权限；其中未列出 PROCESS_VM_READ。故当前不能仅凭这份资料承诺通过该接口剥夺所有读取权限，具体权限行为还需受支持性与实机验证。[权限列表与限制](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/wdm/ns-wdm-_ob_pre_create_handle_information)

驱动发行另有微软签名与测试流程，也增加安装和维护成本。[驱动签名政策](https://learn.microsoft.com/en-us/windows-hardware/drivers/install/kernel-mode-code-signing-policy--windows-vista-and-later-)

默认插件路线不依赖驱动、外部常驻服务或管理员权限。驱动仅保留为另一个产品能力与体验条件下的研究分支，不能借此宣称当前插件已经全量可观测。

## 隔离执行增强分支

除“先探测再响应”，还应研究“敏感部分本来就不在普通宿主可读的内存中”。这是另一种防护边界，不是窥探通知机制。

Windows VBS Enclave 能将应用的敏感部分置于隔离区域，官方说明其可与宿主和系统其他部分隔离。截至本轮核对，要求 Windows 11 Build 26100.2314 或以上、或 Windows Server 2025，以及启用 VBS/HVCI；开发还涉及专用工具链和签名。[VBS Enclave 官方条件](https://learn.microsoft.com/en-us/windows/win32/trusted-execution/vbs-enclaves)

工程判断：kingsSafe 可以研究将少量秘密管理或符合限制的纯计算自动生成到隔离组件中，再由构建产物自动加载。当前没有证据说明可自动搬入任意 Unity 业务或整个游戏进程。官方开发指南要求相应宿主、隔离 DLL 与签名，不能把普通原生 DLL 标为已隔离。[开发与签名指南](https://learn.microsoft.com/en-us/windows/win32/trusted-execution/vbs-enclaves-dev-guide)

关键验收是敏感明文是否返回普通宿主、进入日志或落入输入输出缓冲。若保护后的 getter 仍把原值交给普通业务代码，隔离内部存储不能保证调用方看不到该值。只有不必导出的秘密和可限制输出的计算，才值得进一步验证安全收益；接口调用和边界复制成本单独测量。

这条路线可能保持团队不改业务代码，但会缩小运行机器范围，并增加实现和发行成本。不能要求正常玩家为默认版本手动修改系统安全设置，也不能在隔离不可用时静默退回普通内存后继续宣称相同强度。

Android Keystore 可保护密钥材料并在应用进程外执行相关密码操作，安全硬件支持取决于设备与算法；它并不提供任意游戏字段的隔离执行。[Android Keystore](https://developer.android.com/privacy-and-security/keystore)

增加 P8 研究：先以自有小型任务比较普通内存与 VBS 隔离，检验宿主可见内容、签名与平台条件、返回值泄露、代价和失效处理；通过后才研究自动提取受限纯计算。不得用密钥隔离样本替代整个游戏内存的防窥探声明。

## Android 与 iOS 路线

| 平台 | 可以优先研究 | 不能直接沿用的推断 | 必须实测 |
| --- | --- | --- | --- |
| Android | 发布构建调试配置、公开调试信号、所选数据与代码的完整性校验、随包原生组件 | Root 或被控制环境中的所有读取都能被普通应用发现；Windows PAGE_GUARD 可直接移植 | 多系统版本与 ABI、生命周期、合法诊断、正常与受控被攻环境分别测试 |
| iOS | 分发签名与调试权限核查、公开接口范围内的检测、构建期插桩和运行校验 | 开发签名实验等同于 App Store 分发能力；私有反调试接口可以默认使用；原生库等于内核权限 | 开发与分发签名、真机、不同系统版本、启动与恢复、发行审核与兼容性 |

Android 应用隔离由系统内核执行，原生代码同样运行在应用沙箱内；原生插件不会因此获得跨进程或内核权限。[Android 沙箱](https://source.android.com/docs/security/app-sandbox)

Android 发布产物应核查 android:debuggable=false，避免把默认系统隔离或关闭调试本身记为 kingsSafe 特有的探测效果。[Android 调试配置](https://developer.android.com/privacy-and-security/risks/android-debuggable)

iOS 开发与分发签名的调试权限不同。Apple 技术支持说明开发描述文件可允许 get-task-allow，而分发描述文件包括 Ad Hoc 不允许；测试应区分签名方式，不能只看 Debug 或 Release 标签。[Apple 签名与调试权限说明](https://developer.apple.com/forums/thread/823069)

App Store 指南要求公共 API 按预期用途使用。OWASP 列举了反调试研究手段，不代表每个手段都是可发行 API，更不代表审核保证。[Apple 2.5.1](https://developer.apple.com/app-store/review/guidelines/)

Apple 归档 QA1561 不建议用 exit 实现正常退出，并提醒可能不执行常规终止回调、导致数据未保存。该资料已不再更新，只作为历史体验与数据风险依据，不能独立决定当前系统上的安全处置实现。[Apple QA1561](https://developer.apple.com/library/archive/qa/qa1561/_index.html)

目前没有三平台统一的“窥探通知”适配实现；iOS 与 Android 的强制终止策略单独做产品与技术验证，不能用 Windows 自终止样本替代。

## 建议架构

| 部件 | 职责 | 零改动要求 |
| --- | --- | --- |
| Editor 接入 | 注册构建扩展，扫描平台和静态兼容条件，生成默认保护配置 | 原 Build 入口不变，不要求手工标注业务字段 |
| 程序集变换 | 对可证明支持的访问路径插桩，保留所需运行组件 | 只改构建副本，原代码不替换为自定义类型 |
| 受保护存储 | 为可处理数据维护内部表示与校验，必要时使用独立区域 | 不保留长期权威明文镜像，不改变外部存档契约 |
| 平台监测 | 获取调试、访问及完整性信号 | 使用平台适配，不假定三平台检测能力一致 |
| 响应策略 | 区分不确定信号与确证事件，执行对应响应 | 默认行为随构建产物生成，不要求业务接入回调 |
| 构建报告 | 列出已保护、未覆盖、失败与运行组件版本 | 无法满足默认必要范围时失败，不静默成功 |

Unity 官方允许在 Player 脚本编译后读取或修改本次托管程序集，但会增加构建成本。这是自动插桩的依据，不是对所有类型变换兼容的保证。[Unity 程序集回调](https://docs.unity.com/en-us/engine/6000.3/script-reference/unityeditor/build/ipostbuildplayerscriptdlls/onpostbuildplayerscriptdlls)

首轮只研究普通自有托管类中的非序列化整数字段，禁止以改源码、添加安全字段属性、显式安全类型或手写 Runtime 初始化作为产品接入步骤。ref/out、字段地址逃逸、反射、序列化、native interop、Burst 与 Jobs 等在不能自动证明兼容时不变换，并明确计入未覆盖范围。

仅增加编码和校验不能预设检出冻结：一个旧值可以仍然自洽。业务进展、代际状态与重放检测需单独验证；若某种判断必须由业务提供规则，则不满足当前零业务改动目标，应记录该路线限制。

逻辑混淆用于提高监测点定位与修补成本，资产加固用于减少静态资源直接暴露。它们与本专题配合，但任何一层的成功不替代另外两项核心能力验收。

## 终止响应如何评价

保留三种实验策略，比较它们的效果与代价，不预先把随机崩溃当成最佳实现。

| 实验策略 | 含义 | 主要用途 |
| --- | --- | --- |
| 仅观察 | 记录信号，不改变业务 | 测量误报、时序与归因，开发诊断 |
| 访问阻断 | 在受支持的数据或资源访问点拒绝异常操作 | 检验是否在非法收益生效前阻止 |
| 自身终止 | 达到预定义条件后终止当前游戏进程 | 检验缩短持续观察窗口，保留用户提出的强响应目标 |

只处置当前应用，不终止其他进程、不破坏存档、不改变系统设置、不自动封号。弱计时信号、进程名称、一次页面驻留变化不单独视为攻击确证。

进程内状态机只能防止正常执行中的策略混乱，不能据此获得对更高权限攻方的信任根。攻击者可尝试暂停、修改或绕过监测与终止路径，必须有对应实验。

强制终止和受控退出分别记录。强制终止不保证所有 Unity 生命周期回调或业务提交完成；Microsoft 也说明无条件终止可能影响 DLL 全局状态与挂起 I/O。[Microsoft 终止语义](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-terminateprocess)

对于“源码完全不改”和“未知项目任何时点都可立即终止且无数据损坏”这两个同时成立的要求，当前没有通用证据。实验必须包含存档、下载、网络提交、暂停恢复与正在写入时的终止。需要业务定制清理才能安全的场景，应判定不满足当前产品约束。

## 从读取结果到时序证据

固定记录以下时间：读取开始、读取完成、目标检测、策略决定、目标退出。跨进程时钟需统一并记录采样误差；进程暂停期间不能假设检测线程仍在运行。

报告以下独立结论：

- 读取方是否拿到有效明文，获得哪些字节与对象，能否完成任务。
- 目标是否探测到相应事件，是否正确归因。
- 在检测之后何时响应，是否成功停止后续观察。
- 是否在数据泄露前阻止首次有效读取。
- 是否阻止非法业务收益，是否影响正常功能与已有数据。

读取完成之后才退出，可作为响应成功，不能算首次读取被阻断。没有有效检测记录的自然崩溃、工具故障或系统拒绝，不计入插件探测成功。

## 原型与退出条件

| 阶段 | 实验 | 进入下一阶段条件 |
| --- | --- | --- |
| P0 零改动基线 | 同一 Unity 工程不接插件与只加插件分别构建，记录源码和资源摘要 | 插件之外不需业务改动；完整与增量构建均能追踪保护产物 |
| P1 独立原生探测 | Windows 双进程读取独立可读页、守卫页、诱饵页，区分本进程与外部访问 | 有原始事件与读取结果；归因不能成立时收窄或淘汰信号 |
| P2 Unity 嵌入 | 插件自动带入运行组件和监测，不要求场景挂载或业务调用 | IL2CPP Player 能启动、运行、退出，正常回放通过 |
| P3 数据自动变换 | 自动处理受限字段，测试改值、冻结、重放和合法读写 | 完整覆盖声明对象的访问，无长期明文镜像，外部契约保持 |
| P4 响应验证 | 调试与读取发生后对比观察、阻断、自终止三种策略 | 独立记录读取与响应时序，强制退出不冒充保密成功 |
| P5 正常环境 | Profiling、录屏、崩溃收集、输入法、覆盖层、卡顿和暂停恢复 | 正常样本无保护导致的退出，功能回放和数据完整性通过 |
| P6 攻方验证 | 传统工具、人工与 REA 类工具的已知源码任务 | 工具适配有效，绕过与权限如实记录，不把工具失败算防护 |
| P7 移动端 | Android 与 iOS 独立真机、签名与平台适配 | 分平台出结果，不从 Windows 直接外推 |
| P8 隔离增强 | 独立小型 VBS 任务、宿主可见内容与自动调用接入 | 系统条件、签名、性能及输入输出泄露分别通过后再扩展 |

P1 的可控原生程序用于验证操作系统语义，不算 Unity 插件产品已经完成。P0 与 P2 必须重新证明产品接入形态。任何要求改业务代码的做法可以是机制对照，不计入零改动通过率。

## 验证矩阵

| 编号 | 任务 | 判定与原始证据 |
| --- | --- | --- |
| O01 | 无攻击正常运行、系统负载与后台软件组合 | 记录事件、正常会话和小时数、误终止；任一确定误伤阻断该配置发布 |
| O02 | 用户态调试器启动前与运行时附加、暂停与恢复 | 检测及终止时序；明确无法执行检查的暂停窗口 |
| O03 | 外部只读：单地址、连续区域、批量与重复扫描 | 实际读取数据、异常归属、调用返回和目标日志；首读成功即不得声称该任务读取被阻断 |
| O04 | 守卫页与合法读取并发、保护恢复与重入 | 首次与后续访问分开；死锁、重入与误报单独失败 |
| O05 | 修改、冻结、旧值重放与返回值篡改 | 目标收益、校验与动作时点分别记录，与 M01 到 M06 对照 |
| O06 | 修补监测器、修改事件结果、移除终止点 | 已知源码绕过记录；仅存在检测 API 不算有效防护 |
| O07 | 有权限差异的读取与既有进程句柄 | 普通用户、提高权限、内核实验分别标注；不混算成功率 |
| O08 | 终止时进行存档、下载和网络提交，随后重启 | 原有文件和业务结果有效；未执行回调不能被忽略 |
| O09 | Android 与 iOS 的开发、分发、正常与受控攻击环境 | 真机、签名、系统、可用 API、读取证据与发行结果独立记录 |
| Z01 | 仅导入插件后原入口构建 | 业务源码、资源与既有配置摘要不变，除包引入外无人工接入步骤 |
| Z02 | 清洁、增量、批处理和构建失败重试 | 组件不被裁剪、插桩不重复、不污染缓存，保护覆盖稳定 |
| Z03 | 反射、序列化、字段地址与原生访问等不支持样本 | 构建报告完整，不能把未覆盖对象列为已保护 |
| Z04 | 移除插件并用原入口重新构建 | 原项目仍可生成基线，不遗留必须的业务迁移改动 |

实验前锁定 OS、Unity 完整补丁、架构、工具权限、签名、检测频率、重复次数、延迟阈值、性能预算和任务成功条件。已有资源与内存防修改标准继续生效。

新增指标包括检测率、误终止率、首次有效读取成功率、检测和退出延迟、触发前获得的内容、CPU、异常次数、P95/P99 帧时、GC、峰值内存与构建开销。有限会话中零误伤只表示观察结果，不外推总体零误报。

结果状态为 pass、fail、inconclusive、not-run 或 out-of-scope。工具不存在、不兼容、权限不足、样本不能正常解读都不能记为探测成功。

## 投入与成本判断

| 工作 | 相对投入 | 成本来源与依赖 |
| --- | --- | --- |
| 固定 Windows 环境的调试状态与自终止原型 | 较低 | 原生接口、事件记录与测试框架；不等于检测效果已成立 |
| 独立内存区与守卫信号归因 | 中高 | 双进程、并发、异常语义、合法访问与误报；性能可能决定淘汰 |
| 无业务改动的字段自动变换 | 高 | 静态分析、访问覆盖、IL2CPP、裁剪、序列化与增量构建兼容 |
| 防监测器被定位与修补 | 高且持续 | 与逻辑混淆配合、跨版本对照、已知源码攻方验证 |
| Android 与 iOS 发行级适配 | 高 | 真机矩阵、签名、平台 API、诊断与发行测试 |
| VBS 隔离执行分支 | 很高且缩小兼容范围 | 受限计算转换、边界调用、系统功能、专门签名与工具链 |
| Windows 驱动分支 | 很高且改变产品条件 | 签名、系统级维护、安装与权限，不能隐含在普通插件成本内 |

这是相对工程量判断，不是排期或报价。原型 P0 到 P2 决定是否继续投入；若只能通过大量异常触发获得弱扫描线索，需用误报和帧时证据决定淘汰，而不是因已有实现投入继续扩张。

## 设计决策与尚未回答的问题

| 决策 | 当前处理 |
| --- | --- |
| 是否纳入产品研究目标 | 是，作为内存保护的探测与响应方向，不新增第四项产品核心 |
| 是否坚持只加插件 | 是，不能用手改业务代码替代产品验收 |
| 是否研究被观察即终止 | 是，但只对明确事件做实验，不承诺所有窥探均可见 |
| 首轮平台 | Windows x64 IL2CPP，固定 Unity 6.3 补丁；其他平台单独验证 |
| 默认是否依赖驱动 | 不依赖，保持现有无新增管理员权限与安装步骤目标 |
| 是否研究硬件或系统隔离 | 是，VBS 为增强分支，限合格系统与受限任务，不等同于整体内存不可观测 |
| 诱饵与页面信号是否足以直接强制退出 | 暂无证据，先测归因、误报与覆盖 |
| 是否已经证明零误伤或可发布 | 否，所有原型与实际结果均未执行 |

下一步必须由 P0 到 P2 回答三个问题：外部读取是否留下可靠证据；插件是否能在零业务改动下自动带入这些机制；正常运行代价是否可接受。若外部读取无法可靠感知，应保留可验证的调试与篡改检测，不把“所有内存不可窥探”作为发布宣传。

## 资料使用记录

本报告优先使用 Unity、Microsoft、Google、Apple 官方资料及 OWASP 原始标准。接口文档用于确认公开语义，kingsSafe 的覆盖率、保护效果、误伤与性能必须通过原型取得。

OWASP 当前的反调试测试将静态引用、实际运行与鲁棒性区分；仅找到或调用检测 API 不证明难以绕过。研究使用当前 v2 的 0401 与 0402，旧 0089 已弃用。[当前运行测试](https://mas.owasp.org/MASTG/tests/ios/MASVS-RESILIENCE/MASTG-TEST-0402/)

OWASP 的 RASP 说明支持“随应用监测并响应”这一技术类别，也区分 SDK 与编译期插入，但不能据此认定 kingsSafe 已有可用能力。[RASP 原始说明](https://mas.owasp.org/MASTG/knowledge/android/MASVS-RESILIENCE/MASTG-KNOW-0118/)

Apple 运行时安全页面本轮读取受到限流，未据其正文添加新结论；Android 调试页面一度超时，已由 Android 调试配置与 AOSP 沙箱正文补充。Windows Ob 回调与具体读权限的适用性仍为待核实问题，保留不确定性而非自行扩张接口能力。
