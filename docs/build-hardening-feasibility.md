# 只加插件、原 Build 完成三项加固：可行性与实测

研究日期：2026 年 10 月 30 日。结论级别：一手资料核对与一个自有小样本的自动构建机制验证；不构成产品防护、兼容性或性能验收。三项核心仍为资产加固、内存保护、逻辑混淆。

## 1. 当前判断

值得继续研究，不能因为 Unity 没有默认提供，就判断这条路线做不到。Unity 官方明确提供在 Player 程序集编译后读写构建副本的接口，现有 Unity 安全产品也使用这些接口。[S1/S2/S3](#来源)

本轮已在本机 Unity 6000.3.6f1 上实际完成：同一份业务源码、同一个原始 Build 入口，先构建基线，再只加入研究插件，自动处理一个 Bundle、一个普通整数字段和私有方法名称，并运行两个 Player 对照。没有要求业务接入安全类型、属性、加载 API 或挂载组件。

这说明“插件在 Build 中自动准备加固、随产物带入运行组件”的交付链可以跑通。它没有证明任意 Unity 项目只导入插件后，所有资产、所有内存和所有逻辑都能达到有效防护。

产品目标保留为：**只引入插件，沿用原 Build，自动完成受支持范围内的三项加固；功能、资源和原有对外契约保持，性能单独实测。** 下一阶段要用实际覆盖率和攻击结果推进，而不是把“能自动插入代码”当成“三项保护已经成立”。

## 2. Build 在这里承担什么

加固不局限于一次打包前或打包后的文件处理。它贯穿整个构建流程，在适当时点分析资源、处理 Player 程序集副本、生成运行组件和容器，最后完成平台编译与签名。

| 时点 | 插件自动完成的工作 | 后续运行时需要的能力 |
| --- | --- | --- |
| 构建前分析 | 识别资源系统、程序集、契约与危险用法，形成覆盖清单 | 不要求玩家额外操作 |
| 资源内容构建 | 加密认证发行副本，维护依赖、地址、摘要与缓存关系 | 透明解密与加载、认证失败拒绝 |
| Player DLL 编译后 | 在工作副本中改写可支持字段访问、资源调用与逻辑 | 受保护存储、读写校验、变换后的业务逻辑 |
| Linker / IL2CPP 之前及期间 | 保留必要方法、泛型和桥接，验证生成代码 | 正确的 AOT 和原生平台行为 |
| 平台打包与最终签名前 | 纳入资源和原生组件，校验最终保护状态 | 兼容商店安装、运行与更新 |

Unity 的 IPostBuildPlayerScriptDLLs 是明确支持修改 managed assemblies 的接口；官方也指出它会增加构建耗时。[S1](#来源) 但一个 DLL 回调不会自动接管 Unity 原生资源加载、原生插件内存或业务规则。

IL2CPP 会把 IL 转成 C++ 再编译为平台本机代码；所以 IL 处理应在该转换前验证，不能用 Mono 成功替代 IL2CPP 成功。[S4](#来源)

## 3. 三项能力的实现路线与缺口

### 资产加固

首选标准 AssetBundle / Addressables 的内容构建和加载边界。现有 Addressable Shield 文档描述了构建时加密、运行时透明解密且保留原 Addressables 调用，证明这类产品形态有先例；本轮没有购买、运行或审计该产品，不把厂商描述当成独立防护证明。[S5](#来源)

本轮样本验证了直接调用 AssetBundle.LoadFromFile(string) 也可以由插件自动改写到等价签名的加载桥接，无须团队手动替换业务调用。但只验证这一个同步重载、一个本地文本资源 Bundle，不包含所有 Bundle 类型与加载接口。

难点是保持原有加载契约，同时消除发行物中的未保护副本。Addressables 还可能独立构建或更新内容，仅处理 Player Build 会漏掉部分发布路径。[S6](#来源)

Resources 的公开替换入口值得研究。Unity 参考源码有 ResourcesAPI.overrideAPI 以及 Load / LoadAll / LoadAsync 等可扩展方法；引用的是 master 参考源码，不代表已在固定版本实测。这也不能证明内置场景、直接对象引用与所有 native 读取都能同样接管。[S7](#来源)

原工程资源无须重组、发行副本可自动转换，是应继续验证的方向。若内置资源需要新增 Unity native 级方案，应作为独立路线评估；不能暗中修改 Unity 安装或引擎二进制，以维持“导入插件即可”的表象。

### 内存保护

由构建期自动改写适合的字段及全部已知访问点，运行期维护受保护表示和校验状态，是符合零业务改动目标的候选。检测组件可以同样自动进入产物，但“带入监测”与“每次外部读取都可观测”是两件事。

ACTk 的一手手册要求在业务中引入命名空间、替换易受攻击成员类型，并提示序列化迁移可能丢值。这说明关键数据保护机制有既有产品依据，同时也说明我们坚持的自动接入比常见手工类型替换更严格。[S8](#来源)

本轮已验证普通自有类的一个 int 字段可以不改源码而自动适配，并在下一次业务读取前拒绝单独改值。仍未解决或验证：

- 任意 ref/out、字段地址逃逸、反射、原生直接写入、跨程序集引用、显式布局、并发读写，以及 Burst / Jobs / NativeArray。
- Inspector、场景、存档、JSON、网络协议原有数据布局与格式的兼容；保留原字段名不等于保留语义。
- 自动识别哪些字段影响公平，以及怎样判断一次“看起来合法”的修改违反了游戏规则。
- 完整旧状态回放、协调修改、返回值替换、校验点补丁与保护器自身被修改。

本轮反例已经确认：**简化的值编码加静态校验不足以阻止协调修改和完整旧状态回放。** 不得将这个样本发布为抗外挂方案。

对外部读取的检测与自终止，继续按[内存专项研究](memory-observation-research.md)推进；本轮没有执行双进程窥探，也未验证自终止。原生平台信号和字段保护需要分开设计、分开验收。

### 逻辑混淆

这是构建自动化依据最明确的方向之一。GuardingPearSoftware 的集成文档列出实际混淆使用的 Player DLL 回调、Linker 处理和平台后处理；其兼容文档也明确提示反射、旧存档和 RPC 名称的风险。[S3/S9](#来源)

本轮只证明了私有方法改名可以进入实际 Player 并保持该样本的正常计算。尚未实现控制流变换、常量保护、代码虚拟化，也没有测试 REA / AI 的定位、语义还原、等价重建或补丁成本。名称消失不构成“保护创新”的强度证明。

下一步应先实现自动保留 Unity 消息、生成代码、反射入口、序列化、RPC、泛型 AOT 等契约，再研究控制流与数据表示变换；强变换按实际分析成本与性能选择，不能为了界面中的能力名称而堆叠无效变换。

## 4. 本轮可复现实验

源码与复现说明见 [Unity 自动构建研究样本](../research/unity-build-probe/README.md)。仅在自有样本上实验，未运行第三方保护器或修改 Unity 安装。仅需本机已有的官方 Unity；Cecil 从其安装中复制到研究插件 Editor 目录，不随公开源码分发。

环境：macOS arm64；Unity 6000.3.6f1，修订 bbb010bdb8a3；Mac Standalone universal（x64 + arm64）Mono，在本机默认 arm64 运行，未验证 x64 运行；关闭托管裁剪；非 Development Player；无图形批处理运行。本机未安装 Windows、Android、iOS 和 Mac IL2CPP 构建模块。本轮不代表项目原定 Windows x64 / IL2CPP 环境已通过。

实验是机制探索，未按完整产品评测预注册，不能事后补填成正式验收。没有使用有阳性对照的提取工具、外部修改器或 REA；没有性能预算与完整场景回归。

| 检查 | 基线 | 加入插件后 |
| --- | --- | --- |
| 原业务文件与构建入口 | 两个业务 C# 文件及原 FixtureBuild.cs | SHA-256 不变 |
| 原 Bundle 输入 | UnityFS 资源包 | 原文件 SHA-256 不变；只改发行副本 |
| 发行 Bundle | UnityFS | KSP1 认证加密研究容器 |
| 原资源加载调用 | LoadFromFile(string) | 构建副本中自动改写为加载桥接 |
| 业务与资源结果 | 弹药 97、得分 298、固定文本 | 完全相同 |
| 字段原始存储是否等于 97 | 是 | 否；固定 XOR 编码，仅作机制试验 |
| 单独把原始存储改为 999 | 原业务使用修改值 | 下一次 Fire 读取时拒绝 |
| 同时改值与校验状态 | 无该保护机制 | 可绕过，业务接受 999 后的消耗 |
| 回放全部字段旧状态 | 无该保护机制 | 可绕过，静态校验无法判别进展 |
| 修改密文的受控认证检查 | 不适用 | 拒绝，未将错误明文交给 Unity |
| 原私有 Score 名称 | 可反射找到 | 名称消失，正常业务结果保持 |
| 不改业务、插件再 Build | 不适用 | 已重复构建并运行，仍有处理与相同结果 |
| 本地签名 | 原 Unity 临时签名 | 插件重新进行本地 ad-hoc 签名，严格验证通过 |

插件实际改写一个字段的七个访问点、一个资源加载调用，并改动私有方法名称。实验代码尚无完整保留分析；其中一个改名对象是 Unity 生成的辅助方法，不应据此认定生成代码处理安全。正式实现必须独立识别并保留这些契约。

记录位于 [机器可读结果](../research/unity-build-probe/results-2026-10-30.json)；详细本地日志与 app 在该目录 artifacts/，不纳入源码分发。另从新建空工程完整执行 reproduce.py，基线、导入插件后的构建及重复构建均运行并通过同一证据检查，不依赖调试期间的手工补丁。

### 两个直接改变设计的发现

**普通日志也可能生成字段地址访问。** 初始保守筛选因 Int32.ToString() 的 ldflda 而跳过目标字段；保持原业务代码不变，插件在构建副本中把这一已知只读模式转成局部副本，再改写字段访问，样本通过。其他地址用法仍不能照搬处理。由此增加编译器输出用法矩阵，而不是让团队改日志满足演示。

**产物后改资源会破坏已存在的签名。** 初次后处理后，codesign --verify --deep --strict 报告资源封印无效。研究插件已自动为自己的 Mac 样本重新做 ad-hoc 签名并通过验证。这个修正只证明本地样本流程；没有证明 Developer ID、公证、iOS、Android 或原有发行签名流程兼容。产品必须在最终平台签名前完成处理或有明确的自动签名集成。

### 刻意保留的弱实现边界

资源实验使用 AES-CBC + HMAC-SHA256 的完整内存容器，密钥是源码中的公开 fixture 常量。它只验证接入、往返和损坏拒绝，**不具备发行密钥安全性**，不能证明抵抗已知源码定向提取；完整内存加载也不满足正式分块 Stream 的内存目标。

字段实验使用固定 XOR 与互补校验，没有随机重编码、防重放机制或可靠独立信任源。攻击者可计算合法表示，完整旧状态仍自洽；真实运行中也会存在临时明文。结果只能支持特定单写拒绝，不能支持抗搜索、抗冻结、抗读取或全权限防护。

源码指纹覆盖上述两个业务文件、一个原始构建入口与输入 Bundle。样本构建入口本身会生成场景和资源数据，不能把这几个指纹扩大为完整工程的所有配置与文件均已验收无变化。

## 5. 为什么 Unity 未默认提供，不能作为反证

没有查到 Unity 官方对“为何没有默认提供这三项完整加固”的明确解释，不代替官方推断商业动机。

可以从公开接口与本次实验观察到：这需要游戏相关的保护范围、跨平台运行组件、保留规则、签名、性能控制以及持续安全验证。引擎提供编译与加载扩展，不意味着自动知道哪些数据属于核心规则，也不意味着能改变操作系统的内存访问权限模型。

合理的工程判断是：**构建期自动交付具有基础，真正困难在于自动适配与持续防护效果。** 这个判断既不支持“一个 Build 回调就全解决”，也不支持“引擎没做，所以第三方不能做”。

## 6. 后续研究顺序与决策门槛

| 顺序 | 研究任务 | 进入下一阶段的实际证据 |
| --- | --- | --- |
| B0 已完成的机制探针 | 同源、同入口，插件自动带入三条机制及反例 | 本报告与源码；仅限定 Mac Mono 小样本 |
| B1 Windows x64 IL2CPP 闭环 | 锁定 6000.3.6f1，验证真实 DLL→Linker→IL2CPP→签名；干净、增量、关闭保护、脚本变更构建 | 实际 Player 启动、源指纹、覆盖报告；不以 Mono 替代 |
| B2 资源零改动首版 | 同步/异步/依赖/卸载、Stream 随机读、缓存、Addressables 独立内容构建；扩大纹理/音频/Prefab/场景样本 | G1/G2/G7 对应任务；直接提取阳性对照；R07/R08 披露；性能预算固定后实测 |
| B3 受保护字段的兼容边界 | 普通字段默认值、checked/unchecked、跨程序集、ref/out、序列化与协议；先报告不能处理的对象 | 不改类型/调用/原数据，覆盖明确，无静默漏保护 |
| B4 内存抗绕过 | 外部搜索/修改/冻结、自洽回放、协调修改、返回值和校验点补丁；另测探测与自终止 | 分别记录使用前拒绝、非法收益、首次读取和误终止；负例不得以告警代替 |
| B5 逻辑与 REA 验证 | 自动保留规则、受限控制流/表示变换；固定传统与 AI 分析任务及预算 | 业务等价，定位/还原/篡改成本有独立数据，名称变化不单独通过 |
| B6 移动与发行 | Android / iOS 实机、签名/更新/商店路径、正常设备矩阵 | 每个平台独立报告；不能由桌面结果推定 |

B1 与 B2 维持首发工程优先级；B3 到 B5 可提前做隔离研究，不降低三项核心地位。本轮不安装缺失的大型构建模块、不替代团队办理平台授权与签名，也没有因此宣称跨平台验证完成。

若某些路径无法自动兼容，先明确未支持并阻断必须覆盖的发行构建，再研究自动适配。不能通过要求修改业务源码，悄悄放宽原产品目标。若关键数据的有效性必须依赖游戏语义或服务端权威，则明确提出这是额外架构条件，不能伪装成通用插件已经提供。
