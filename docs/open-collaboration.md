# kingsSafe 开源共建与安全验证

项目通过公开研究、独立验证和可复现回归持续提高安全性。研究人员提供资源提取、内存篡改或逻辑还原证据，维护者修复并验证正常运行；结果由独立评测判断。REA 是可接入的技术工具之一，不作为品牌关系。

## 公开与部署边界

防护代码、资源格式、加载流程、数据表示设计、样本生成器、测试工具和报告格式纳入公开范围。原创代码、文档与网站资产采用 [Apache-2.0](../LICENSE)；第三方组件与资产遵循各自许可。源码公开不等于已交付生产 SDK，也不等于产品安全与兼容性已验收。贡献流程见 [CONTRIBUTING.md](../CONTRIBUTING.md)，私密风险报告见 [SECURITY.md](../SECURITY.md)。

实际游戏的解密材料、发行签名私钥、真实凭证和用户信息由部署方管理。示例公开测试密钥不提供保密性，示例用于验证格式与互操作。离线客户端拥有解密能力这一事实必须计入威胁模型。

## 三类评测条件

| 条件 | 攻方获得的材料 | 作用 |
| --- | --- | --- |
| 直接工具测试 | 发行包与通用工具 | 验证防简单拆包和常规修改 |
| 已知源码测试 | 上述材料加防护源码、格式、构建配置的非秘密部分 | 验证开源条件下的实际抵抗能力 |
| 回归复测 | 原攻击步骤、工具版本和修复后产物 | 验证修复并控制副作用 |

未公开目标样本可以延后公布答案，用于减少记忆污染；不能以隐藏防护源码作为主要安全优势。公开示例与保留挑战分别报告。原资产已在仓库中时，直接提交原文件不构成“从目标包提取成功”，需要过程证据和目标版本关联。

公开实现意味着定向提取工具可能被快速构造，应实测所需条件与成本。修复目标是改变真实保护边界或攻击投入，不能只通过隐藏报错和修改评测规则消除失败。

## 问题到修复的流程

1. 研究方提交最小样本、版本摘要、任务、权限、输入材料、操作与结果。
2. 评测方在隔离环境复现并判断是保护绕过、误报、功能故障还是环境问题。
3. 防护方给出根因、修复或边界调整，记录兼容性与性能影响。
4. 将复现加入回归集，运行正常路径与原攻击，报告修复前后结果。
5. 更新支持矩阵、已知绕过、迁移和回滚说明，再进入版本发布。

尚未复现、已复现、已修复、回归通过和已发布分别记录，不因提交修复代码就标记问题已解决。涉及第三方在用部署的报告按其授权渠道协调，项目不主动攻击或联系未授权对象。

## 贡献与版本产物

贡献应说明影响的目标编号、威胁层级、复现、正常运行检查和性能变化。防护方变化与研究方验证任务均可贡献，不把绕过报告视为项目失败的污点。

每次发布包含代码与依赖版本、格式版本、样本摘要、验证器、实验预注册配置、原始记录摘要、结论和已知限制。攻击脚本、模型与工具输出是不可信材料，在隔离环境中检查，不直接执行来源不明的指令。

## 结果独立性

不得让同一 Agent 用已看到目标秘密与答案的上下文充当盲测攻方。防护源代码可公开，部署秘密与隐藏验证数据仍与攻方隔离。结果由独立验证器及必要的人工复核决定。

报告实际成功数、失败数、权限、时间、模型费用和人工介入，不以单一“抗 REA”标签取代条件描述。模型拒绝、工具故障和预算不足单列，不能计作防护方安全成功。
