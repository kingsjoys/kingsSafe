# Unity 游戏资源与数据保护调研

kingsSafe 的三个核心研究方向为资产加固、内存保护和逻辑混淆，分别对应内容提取、关键数据篡改与核心实现还原。传统工具、人工与 AI 辅助逆向共同参与评测，不能以反编译一次失败或代码更复杂证明安全。

## 产品判断

资源防拆包可以围绕具体资产、固定工具和实际加载建立清楚的实验。关键数据防修改可以围绕搜索、写入、冻结与最终业务收益验证。两者分别对应内容资产损失与作弊行为；逻辑混淆独立对应算法、机制和关键实现的保护，三者并列为核心。

方法改名只减少部分语义线索，不能替代资源保护或数据校验。逻辑混淆保护核心算法与独有机制，也覆盖密钥处理、加载和校验路径；其价值由实际定位、还原和篡改成本验证。

## 逆向能力变化

REA 将 Agent 与现有分析引擎连接，返回代码、调用与引用证据，支持继续调查与验证。公开案例包括游戏函数重建，但不是现代商业游戏完整加固被普遍突破的证明。[R01](https://github.com/morluto/rea)

已有研究展示了模型对混淆代码的分析能力，也显示任务和变换之间存在差异。函数名称恢复、伪代码简化、完整程序理解与完成实际攻击不是同一指标。[R04](https://globals.ieice.org/en_transactions/information/10.1587/transinf.2025KBP0015/_f)、[R05](https://arxiv.org/abs/2604.08083)

SRE Bench 强调规模、尝试条件和独立验证的重要性；VMSpec 则表明传统自动化去虚拟化也在发展。评测因此保留多种攻方方法和失败轨迹，不能只盯某一个 Agent。[R06](https://arxiv.org/html/2608.11469v2)、[R07](https://arxiv.org/abs/2610.29566)

REA 分析可以本地运行，模型服务的数据政策另行适用。源码可以按开源目标公开，实际部署密钥与隐藏验证数据不能因此混入攻方上下文。

## 现有体系的启示

腾讯 ACE 的公开能力涉及关键代码、运行时、资源和 Unity 保护，并支持构建流程集成。Denuvo 同样提供多层保护和检测。不能把成熟厂商简化为固定壳，也不能由公开文案判断其针对 AI 的内部研究进展。[R02](https://www.anticheatexpert.com/products/lite-anti-cheat-pc)、[R03](https://cloud.tencent.cn/document/product/654/30316)、[R08](https://irdeto.com/video-games/denuvo-anti-cheat)

OWASP 将混淆和运行时反篡改视为纵深防护，强调不能替代可靠安全架构。其移动安全原则可参考，但不是 Windows 游戏的认证标准。[R09](https://mas.owasp.org/MASVS/11-MASVS-RESILIENCE/)

联网游戏还可结合服务端权威判定和信息最小化。Riot 的 Fog of War 展示了降低不必要客户端信息暴露的思路；这属于业务架构，不会由通用资源加密器自动完成。[R10](https://technology.riotgames.com/news/demolishing-wallhacks-valorants-fog-war)

## 资源保护依据

Unity 支持通过自定义 Stream 读取 AssetBundle，也提供 Addressables 资源 provider 扩展。可研究在标准边界加入容器认证与按需解密，但随机读取、线程访问、缓冲、依赖和卸载生命周期都属于兼容条件。[U08/U09](sources.md)

使用认证加密是容器候选路线，Unity IL2CPP 上的密码库支持仍要验证。资源在运行时以可使用形式存在，离线客户端也需要解密能力，因此开源项目应分别测直接工具提取、已知源码定向处理和运行时提取。容器改后缀或使用未知格式不是充分的安全依据。

## 内存保护依据

Windows 对进程内存读写有权限控制。进程内数据表示与校验可以增加部分攻击成本，但不能据此承诺抵抗管理员、注入补丁、内核或 DMA 访问。[W01](sources.md)

数据存储变化应与读取检查、业务期望及处置配合。冻结一份有效旧状态未必破坏静态校验，因此冻结要单独测试。保护机制必须保持合法运算、存档和协议语义，而不是只让搜索器找不到数值。

Unity 的反射、AOT、序列化与 Linker 约束意味着构建插桩需要受限白名单和保留规则，不能自动覆盖任意字段。[U01/U02/U05/U06/U07](sources.md)

## 当前路线比较

| 路线 | 作用 | 当前安排 |
| --- | --- | --- |
| Bundle 容器认证加密与配套加载 | 提高直接提取与替换难度 | v0.1 核心 |
| 缓存和密钥交付管理 | 避免保护链被明文副本或共享密钥抵消 | v0.1 必须设计和验证 |
| 关键数据表示与访问校验 | 抵抗部分常规改值，检查业务使用前状态 | v0.2 核心 |
| 逻辑混淆 | 提高关键实现的定位、还原与篡改成本 | 独立核心方向，按路线图研究 |
| 驱动与硬件完整性 | 更高权限攻击面 | 首轮不纳入承诺 |
| 服务端判定 | 限制客户端篡改的业务收益 | 保留独立集成方向 |

当前路线均需用[预先制定的标准](validation.md)验证，尚无 kingsSafe 产品安全验收结果。2026 年 10 月 30 日的[构建加固可行性与实测](build-hardening-feasibility.md)已在一个 Mac Mono 小样本上验证自动接入，并实测简化内存方案的协调修改与完整旧状态回放绕过；它不代表 Windows IL2CPP、外部内存探测或性能已经通过。开源实现、共同任务与可复现修复记录，是持续验证提升安全性的基础。
